На каком языке программирования планируется реализация? (Python, Node.js, Go?)
Какие LLM API будут использоваться? (OpenAI, Anthropic Claude, локальные модели через Ollama?)
__
Будем использовать Оупенроутер, модель Грок Фаст с возможностью тестировать и другие.

2. Хранилище данных
Какая база данных для хранения квантов? (SQLite для прототипа, PostgreSQL для продакшена?)
Как хранить связи между квантами? (граф в JSON, отдельная таблица связей, графовая БД?)
__
на MVP SQLITE, но сразу закладываем возможность апгрейда на прод до редис+ постгри
Связи между квантами хранятся внутри самих квантов, пример:
```json5
{
  "inject": {
    "id": "Маша",
    "body": {
      "mother": "тяжело больна"
    },
    "links": {
      "Таверна_Атарикс": "больше не работает",
      "Елена": "Мать, тяжело больна неизвестной болезнью. нуждается в уходе"
    }
  }
}
```
Соответственно в кванте Елена будет обратная ссылка "Маша":"Дочь, уволилась с работы чтобы ухаживать круглосуточно" - создаются, меняются квантователем парно - изменил одну - обновляй и другую, передача краткого контекста обязательна.

3. Механизм инъекций
Как именно работает inject в квантах? Это простой merge объектов или есть специальная логика?
Что происходит при конфликте - например, если в body.family было "больная мать", а приходит "уехала к матери"?
Поддерживается ли удаление полей через инъекции?
__
Нужна специальная логика, квантователь может создать, переписать квант целиком. но для обновлений дает команды - типа "append_Маша_body":"просила игрока найти лекаря для матери", но может и переписать, и удалить по аналогии. в твоем примере догично переписать, оставив одну запись "replase_Маша_body_mother":"бросила работу в таверне и уехала ухаживать за матерью"
Синтаксис обсуждаем, но он должен быть прост и понятен для квантователя и удобен для Json. При парсинге менеджер квантов понимает что и где нужно сделать, и совершает операции с базой.

4. Граф связей
Какая максимальная глубина при "подтягивании локальных связей"?
Если запрошен квант "Маша", который связан с "Таверна_Атарикс", который связан с "Бармен_Игорь" - возвращаются все три или только первые два?
__
Нулевая, ГМ получает строго те N (10, но вынесем в конфиг для настройки)квантов. которые запросил. Но квант Маша будет содержать в себе семантически значимые связи, главный агент по контексту понимает, если речь про таверну - ее квант и бармена могут потребоваться, запрашивает на следующий ход. Если про мать - запрашивает ее квант. Соответственно через ход он может запросить кванты болезни и квеста о поиске лекарства. Это очень тонкий момент - ГМ выбирает наиболее релевантные предугадывая, куда движется сюжет, а вместе с ними получает и отсылки к новым уточняющим квантам, память работает в динамике, не стремясь "вытащить" все втупую за 1 ход.

### 10. Структура БД

- `turns` (id, session_id, turn_number, user_message, agent_reply, timestamp)

Нормально?
__

Да, только не telegram_id а platform_id - телеграм будет одной из возможных оболочек

### 11. Квантователь: контекст и триггеры
- Что именно получает квантователь: самари + последние N ходов + список активированных квантов (с их содержимым)?
- Триггер вызова: строго каждые 3-4 хода или по какому-то условию (например, появление новых сущностей)?
- Нужна ли очередь задач для квантователя или он блокирует ход до завершения?
__
Основа верна. Системный промпт, причем "сборный", например если пользователь включил 18+ режим и дал информированной согласие, блок меняется с "избегать интимных тем" на "пользователь дал согласие на эротику", или в зависимости от выбранного сеттинга, подставляются разные описания игрового мира.
Триггет таков, "сырое" окно 4-7 квентов, когда их становится 7 - вызываются квантователь и сумаризатор, а окно сокращается до 4. Цифры условные - вынесем в конфиг для точной подстройки.
Квантователь и сумаризатор работают в фоне. Пока пользователь читает 7-й ответ, пишет ход, они обновляют данные. Если не успели - не страшно, просто ГМ получит 8 сырых ходов - все обновления в них есть.

### 12. Формат команд квантователя
Предлагаю такой синтаксис команд:
```json5
{
  "commands": [
    {
      "action": "create",
      "quant_id": "Елена",
      "type": "npc",
      "body": {"role": "мать Маши", "status": "больна"},
      "links": {"Маша": "дочь, ухаживает за ней"}
    },
    {
      "action": "update",
      "quant_id": "Маша",
      "operations": {
        "body.role": {"op": "replace", "value": "безработная, ухаживает за матерью"},
        "links.Таверна_Атарикс": {"op": "replace", "value": "уволилась"},
        "links.Елена": {"op": "add", "value": "Мать, тяжело больна"}
      }
    },
    {
      "action": "delete",
      "quant_id": "Старый_квант"
    }
  ]
}
```
Устраивает или сделать проще/иначе?
__
Нужна специальная логика, квантователь может создать, переписать квант целиком. но для обновлений дает команды - типа "append_Маша_body":"просила игрока найти лекаря для матери" - действие, квант, место, значение, все одной строкой. Распарсить можно и без ИИ. 

### 13. Валидация имен квантов
- Какие символы разрешены в именах квантов? (латиница, кириллица, цифры, подчеркивания?)
- Нужна ли автоматическая нормализация (например, "Таверна Атарикс" → "Таверна_Атарикс")?
__
Лучше если квант будет называться ровно так, как в контексте. Во всяком случае на уровне агентов. Для устойчивости лучше применить эластичный поиск, чтобы оба варианта прошли, но в игре ГМ должен писать Таверна Атарикс, потому - гораздо лучше если и квант будет называться так.


### 14. Несуществующие кванты
Что делать, если ГМ запросил квант, которого нет в базе?
- Вернуть пустой результат?
- Сообщить ГМ об отсутствии в следующем контексте?
- Автоматически создать заглушку?
__
Вернуть остальные кванты, но это скорее задача промптинга, чтобы не допустить такого. ГМ должен запрашивать то, что видит в JSON квантов строго, либо то что =выделено маркерами= - такие названия не склоняются не спрягаются, пишется ровно то, что можно запрашивать.

### 15. Суммаризатор
- Параметры: при скольких сырых ходах срабатывает (вы написали 7→4)?
- Формат самари: простой текст или структурированный с якорями на кванты?
- Хранить все самари цепочкой или только последнее?
__
Суммаризатор работает в 2 режимах, если длина самари меньше порога (20000 символов) получает только последние сырые ходы, и предпоследнее свое дополнение (чтобы знал что уже записано) и дописывает их самари, которое приклеивается к основному. Если больше - вызывается с другим промптом, получает все самари и сырые ходы, и переписывает целиком, при этом более давние события "просушиваются". Названия квантов при этом стремится записать неизменно, выделяя в тексте =квант=. Какие маркеры использовать пока не уверен - нужно чтобы без экранирования в json. и не из разметки маркдаун во избежание проблем. Важно, что Json тут понятие условное, это скорее структурированный текст, даже если будет синтаксическая ошибка, LLM интерпретирует ее правильно, но код от таких ошибок не должен ломаться - работаем как с текстом.
